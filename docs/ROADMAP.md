# Pikambler｜開發地圖 × 學習地圖

**產品 Roadmap：v1.0 發布目標；文件草稿版本 `draft-1`**
原規劃：2026-10-22；依產品決策更新：2026-10-23
目前狀態：Stage 00.01～00.11 已確認，**00.12 文件仍待人工驗收**；Stage 01～17 未開始。
定位：**從零親手開發、手機優先、純前端、理論等機率、本機優先、零固定月費目標**。

> **文件分工**：[`SCOPE.md`](./SCOPE.md) 是「做什麼、為何、什麼不做」的產品契約；本文件是「何時學習、何時實作、如何驗收」的路線圖。如果兩份文件矛盾，先以已確認的產品決策修正它們，不能選方便的一邊執行。

> **一句話產品定義**：玩家選一個**單一普通飾品系列**的挑戰，設定適用款式總數 `N` 與初始已擁有的款式，逐筆登記**看見的結果**（不問是否收下），並依各款 `1/N`、觀察彼此獨立的**理論模型**產生機率、倒楣程度與高中數學講義。

## 閱讀指南

- **核心主線（Stage 00–15）**：完成後即可宣布 v1.0 正式發布。
- **選修線（Stage 16–17）**：PWA、複數系列、進階機率、雲端帳號等；**不是** v1.0 完成條件。
- 每章都有「學什麼 → 做什麼 → 驗收 → Git 落點」，請不要跳章加功能。
- 每次詢問 ChatGPT 時，可指定：「現在 Stage 06.04，請用教學模式解釋，不要代寫」。
- **人學習，Agent 做文書**：說明、練習、核心 TypeScript、測試理解、Git 操作以人為主；Agent 可協助彙整決策、修正文句、檢查文件一致性。
- **術語**：`N` = 系列的款式總數；`k` = 初始已擁有與後續已登記中不同款式的聯集數。進度為**已觀察進度**，不追蹤是否收下或圖鑑實際解鎖。
- **不再限制純點或探測器**：純點探測器、混合點、自然撿取、生活日誌等來源，若看見的是目標系列結果，都可登記；來源選填，機率計算不使用來源。

## Stage 00｜產品契約與不做清單（00.12 待人工審核）

**學習目標**：分辨需求、資料語意、數學假設、非目標、MVP（最小可行產品）及 Acceptance Criteria（驗收條件）。這一階段不實作核心程式。

- [x] 00.01 **產品定位**：Pikambler 是「Pikmin Bloom 普通飾品觀察日誌＋原創高中機率講義」，不是遊戲真實掉率研究。
- [x] 00.02 **挑戰單位**：一場挑戰對應一個單一普通飾品系列；任何地點或來源的該系列觀察可合併，不要求純點。複數普通飾品系列混抽留到未來。
- [x] 00.03 **款式數與理論機率**：`N` 依系列適用款式清單，**不固定 8**；每款在理論模型中皆為 `1/N`，例如八款時各為 `1/8`。
- [x] 00.04 **獨立性假設**：每次登記的目標系列觀察互相獨立、無保底、無地點或取得來源權重；**是數學前提，不是遊戲事實**。
- [x] 00.05 **初始狀態**：建立挑戰時設定已擁有的不同款式；更早的歷史不補算為本次挑戰的觀察次數。
- [x] 00.06 **登記單位**：玩家每登記一次「看見的款式」，就算模型一次觀察。可事後補登、允許漏記；未登記日不算失敗；日期、來源均不是數學必要參數。
- [x] 00.07 **完成**：模型進度到 `N/N` 即完成；不追蹤是否收下／種植／解鎖。遊戲新增款式可調整 `N`，但不能靜默改寫舊模型的歷史解釋。
- [x] 00.08 **最小功能**：建立挑戰、初始款式、觀察登記、歷史查閱／補登／更正／刪除、機率、原創講義、IndexedDB 保存、JSON 備份、公開手機網頁；取得來源選填。
- [x] 00.09 **非目標**：真實掉率研究、純點地圖、付費、追蹤是否收下；登入／同步／多用戶雲端儲存／排行榜與多系列模型僅未來評估；v1.0 不自行架設後端 API、樹莓派或 LINE Bot。
- [x] 00.10 **隱私**：挑戰與歷史留在使用者自己的瀏覽器；不主動上傳；需告知站點資料可能遭清除、不同裝置不自動同步，平台仍可能處理網路連線中繼資料。
- [x] 00.11 **驗收案例**：以 `5/8 → 連續 5 筆重複 → 6/8 → 7/8 → 8/8` 為教學測試；另含歷史更正、補登、來源不影響公式、`N=7`、匯出還原與遊戲增加款式後的版本處理。
- [ ] 00.12 **本次文件作業**：建立 `docs/SCOPE.md`、`docs/ROADMAP.md` 草稿；**由人類逐項檢核，核准後才勾選完成**。不把「已產生檔案」當成「通過審核」。

**驗收門檻**：可以口頭說清楚觀察事件、新款、`N`、數學前提、不追蹤事項、v1.0 不做項目，並證明本文件與 `SCOPE.md` 無矛盾。
**Git 落點**：Stage 02 初始化 Repository 後，才將核准文件納入第一次 commit；此時不要假裝已建立 PR 或部署。

## Stage 06｜機率引擎（先數學，後介面）（未開始）

**學習目標**：把高中機率寫成獨立、可測試的純函式。輸入 `N`（款式總數）、`k`（已觀察不同款式數）、`m`（預計觀察次數）。

- [ ] 06.01 列清假設：`N ≥ 1`、`0 ≤ k ≤ N`、每筆同系列觀察的款式等機率且相互獨立。
- [ ] 06.02 寫下一次出**未觀察新款**的機率：`(N-k)/N`。
- [ ] 06.03 寫下一次出**重複款**的機率：`k/N`。
- [ ] 06.04 寫在 `k/N` 固定階段，連續 `m` 筆沒有新款：`(k/N)^m`，期間 `k` 不變。
- [ ] 06.05 寫後續 `m` 筆至少一次出現**相對原集合的新款**：`1-(k/N)^m`。
- [ ] 06.06 寫第一次出現新款恰好在第 `m` 筆：`(k/N)^(m-1) * (N-k)/N`（幾何分布）。
- [ ] 06.07 寫等待**下一個新款**的期望觀察筆數：`N/(N-k)`；`k=N` 顯示完成，不除以零。
- [ ] 06.08 寫從目前 `k/N` 到**模型完成**的期望觀察筆數：`Σ_{r=1}^{N-k} N/r`。
- [ ] 06.09 固定階段連續 `m` 筆重複的理論尾端機率只能標為**理論情境罕見程度**，不是玩家實測排名。
- [ ] 06.10 使用 `toFixed` 或 `Intl.NumberFormat` 只格式化顯示，公式內保留原始數值。
- [ ] 06.11 使用 Vitest 為每個公式寫正常、邊界與無效輸入測試。
- [ ] 06.12 核對 `N=8,k=5` 新款 37.5%；`N=8,k=7` 新款 12.5%；`N=8,k=5` 全部完成期望約 14.67 筆。
- [ ] 06.13 核對 `N=7`、`m=0`、`k=N`、負數、`k>N`、不是整數等情況的明確處理。
- [ ] 06.14 數學函式不依賴 DOM、IndexedDB、取得來源或玩家身分。
- [ ] 06.15 不把不同進度階段混用固定 `k`，也不將觀察次數冒稱實際天數／探測器消耗次數。

**驗收門檻**：可在終端機測試公式，並自己解釋為何 5/8 與 7/8 的結果不同、為何漏記資料只具娛樂參考價值。
**Git 落點**：`feat: implement theoretical probability engine`、`test: cover probability formulas`。

## Stage 07｜挑戰建立、觀察登記與歷史修正（未開始）

**學習目標**：把玩家操作轉成可重算的事件，不混入遊戲是否收下花苗的操作。

- [ ] 07.02 讓玩家勾選**起始已擁有的實際款式**，不能只輸入 `5/8` 這個數字。
- [ ] 07.03 顯示目前模型進度 `k/N`、尚未觀察款式與下一筆理論新款機率。
- [ ] 07.04 用款式按鈕一次登記**一筆看見的目標系列結果**；不詢問是否收下／種植。
- [ ] 07.05 自動標示此筆是首次觀察的新款還是重複。
- [ ] 07.06 即時更新模型已觀察進度、目前階段連續重複次數與理論機率。
- [ ] 07.07 顯示觀察歷史、該筆前後的模型狀態；實際發生日期與來源皆可不填。
- [ ] 07.08 支援事後補登、撤銷最近一筆、修改或刪除錯誤觀察。
- [ ] 07.09 避免重複點擊造成意外多筆，必要時提供明確撤銷操作。
- [ ] 07.10 支援多個互相獨立的系列挑戰；同系列的不同純點／混合點／散步／生活日誌結果可以合併。
- [ ] 07.11 達 `N/N` 顯示**模型完成**並保留歷史，不宣稱遊戲圖鑑一定已解鎖；防止誤把同一筆加入新輪。
- [ ] 07.12 驗證示例 `5/8 → 6/8 → 7/8 → 8/8` 對應的新款理論機率 37.5% → 25% → 12.5% → 完成。
- [ ] 07.13 證明不填來源／日期仍可儲存；來源只作回顧欄位，不改變數學答案。

## 每一章通用的學習與 Git 操作規則

### 一次練習的固定流程
1. 確認章節編號（例如 `Stage 06.04`）。
2. 先理解一個概念；讓 ChatGPT 只解釋、出練習、提示，不幫你整段代寫。
3. 自己手敲最小可工作的程式碼，觀察錯誤。
4. 寫／執行對應測試，人工操作驗收。
5. `git diff` 自審，只提交與本章節目標有關的修改。
6. 推送 feature branch、PR、自審、merge；更新 `docs/ROADMAP.md` 進度。**這些 Git 動作從 Stage 02 正式學習，不是假裝 Stage 00 已提交。**
7. 卡住時記錄 `BLOCKER`；不把新發現的問題擴張成跨章節功能。

### 範圍控制守則
- 若問題妨礙當前章驗收 → **現在修**。
- 若問題是未來章的必要工作 → **記錄章節號，屆時處理**。
- 若不在 v1.0 范圍 → **放 backlog，不立刻做**。
- 如果發現原架構決策有致命問題 → **寫 ADR（Architecture Decision Record）簡述原因與替代方案**，不要直接大翻修。

### 核心數學測試基準（示例選 `N=8`，實際模型須支援可變 N）
- 起始 5/8：下一筆目標系列觀察出新款 `3/8 = 37.5%`。
- 起始 5/8：已登記連續五筆完全無新款 `(5/8)^5 ≈ 9.54%`。
- 進入 7/8：下一筆觀察出最後一款 `1/8 = 12.5%`。
- 進入 7/8：再觀察 8 筆至少一次成功 `1-(7/8)^8 ≈ 65.64%`。
- 起始 5/8：從現在到模型完成的理論期望 `(8/3)+(8/2)+(8/1) = 44/3 ≈ 14.67 筆目標系列觀察`。
- 7/8 連續登記 30 筆重複：`(7/8)^30 ≈ 1.82%`。
- `N=7,k=5`：下一筆新款 `2/7`，用於防止把 N 寫死為 8。
- 不能把不同觀察進度的結果全部當作固定 `1/8` 成功率來評估。
- **已登記觀察**可能不完整，理論尾端機率不等同真實玩家排名、真實掉率或真實等待天數。
- 取得途徑（探測器／路過／生活日誌等）不參與數學模型；不記錄有沒有收下。
- 系列清單更新後，歷史模型前提需要保留或明確告知，禁止靜默改寫。

## 技術選擇及成本

| 層次 | v1.0 | 成本／取捨 |
|---|---|---|
| Web UI | 原生 HTML/CSS + TypeScript | 手機優先；練習基礎，避免 React 額外概念 |
| 建置 | Vite `vanilla-ts` | 免費；Node.js 只在開發/建置使用 |
| 數學引擎 | 自寫純 TypeScript 函式 | 免費，易測試 |
| 儲存 | IndexedDB + Repository | 免費、本機隔離；清除網站資料可能遺失。儲存層可供未來替換 |
| 測試 | Vitest + GitHub Actions | 涵蓋 N 可變、歷史重播、備份與回滾；免費配額待實作時核對 |
| 部署 | Cloudflare Workers Static Assets | 純靜態，不自建 API；請在部署時核對當時官方免費限制 |
| 網域 | `*.workers.dev` | 不購買網域即可公開使用 |
| 身分驗證 | 無 | 網址可公開；各玩家資料只在各自瀏覽器；多用戶雲端功能以後再評估 |
| LINE Bot / Raspberry Pi | 無 | 對純靜態站是不必要的維運與故障風險 |
| 備份 | JSON 匯出／匯入 | 日常不必操作；跨瀏覽器人工搬移及恢復用 |
| 普通飾品模型 | 可變 N，單一系列 | 預留系列款式更新，不納入超市複數系列混抽 |
