## 1. 一句話產品定位（00.01）

> Pikambler 是免費、手機優先的 **Pikmin Bloom 普通飾品觀察日誌＋高中機率數學講義**：玩家為單一普通飾品系列設定起始已擁有的款式，逐筆登記後來「看見哪一款」，網站用**明確聲明的理論等機率模型**解釋新款、重複、等待次數與理論上的倒楣程度，並生成原創高中數學應用題與解析。

- 用途：學習與娛樂；不是《Pikmin Bloom》官方工具，也**不**驗證、估計或宣稱遊戲真實掉率。
- 核心價值：將抽象的高中機率、獨立事件、幾何分布與期望值連到玩家自己的**已登記觀察紀錄**。
- 目標使用者：第一版以專案作者個人日常使用為先；發布後任何人可在自己的瀏覽器匿名使用。**公開多人可使用不代表集中收集多人資料**。

## 2. 名詞定義與資料語意（00.02、00.05～00.07）

| 名詞 | 在 Pikambler 中的定義 |
|---|---|
| 普通飾品系列（Series） | 一個可以獨立列舉款式的普通飾品系列，例如洗衣店或墨西哥系列；v1.0 不處理同一類別下多個普通系列互相混抽。 |
| 挑戰（Challenge） | 對應**一個**普通飾品系列的一段個人觀察日誌；可建立多場互相獨立的挑戰。 |
| 款式（Variant） | 該挑戰中一個可識別且不重複的結果；第一版單一系列通常以皮克敏種類／顏色辨識，未來新增種類時可擴充。 |
| `N` | 此挑戰適用的普通飾品款式總數，由該系列在適用遊戲版本中的款式清單決定；**不固定為八**。示例可用 `N = 8`。 |
| 初始款式集合 | 建立挑戰時玩家表示先前已擁有的不同款式；是計算起點，不補算更早的觀察次數。 |
| 觀察事件（Observation） | 玩家看見一個屬於該系列的花苗結果，並決定登記到 Pikambler；**一筆有效登記算一次理論模型中的觀察**。 |
| 新款 | 這次記錄的款式，未出現在初始款式集合或本挑戰依順序排在它之前的已登記觀察中。 |
| 重複款 | 已在初始款式集合或先前已登記觀察中出現過的款式。 |
| 已觀察進度 `k/N` | 初始款式集合與已登記觀察中不同款式的聯集大小 `k`，不等同遊戲實際持有或已解鎖圖鑑。 |
| 模型完成／畢業 | 已觀察進度達 `N/N`；**不保證**玩家在遊戲內真的保留花苗、種植或解鎖飾品圖鑑。 |
| 取得來源 | 可選的個人回顧資料，不影響機率計算；不知道也可以不填。 |

### 2.1 挑戰與純點的關係

- 一場挑戰綁定**系列**，不綁定某個純點、地標座標或某種取得方式。
- 不同純點、混合地標、日常散步或生活日誌等來源，只要**已知觀察結果屬於該挑戰系列**，均可以登記。
- 在「路邊／墨西哥」混合點，**看見墨西哥款式**才記入墨西哥挑戰；路邊結果不算墨西哥的一次失敗。
- 不計算「使用一次探測器會抽到目標類別」的機率；只計算**已知出現目標系列結果之後，款式分布的理論模型**。
- 因此計算單位是「已登記的目標系列觀察結果」，**不是**天數、走路距離、探測器消耗次數或每次探測器的成果數。

### 2.2 登記規則與「既往不咎」

- **唯一必須由玩家選擇的事件內容是款式結果**；所屬挑戰由目前選擇的挑戰確定。
- **不記錄、不詢問**是否收下、種植、丟棄、鍍金或解鎖圖鑑；玩家只要看見該款式即可登記。
- 玩家可在當天或日後補登；事件實際發生日期**選填**，登記時間由系統自動產生，兩者不能混稱。
- 取得方式選填（如純點探測器、混合點探測器、路上看到／撿到、生活日誌、其他或未知），不必強制分類。
- 歷史允許不完整、允許漏記；未登記的事件不會被系統推測、補造或當成零次結果；未觀察／未登記的日子不算失敗。
- 初始狀態以前的重複結果一概不追溯；玩家可以從今天的 `5/N` 開始。
- 編輯或刪除過去的觀察後，新／重複、進度與各階段統計必須從**初始狀態＋保留的事件**重算，不儲存一份獨立可手改的「真實進度」。
- **事件順序**會影響階段統計。對選填的實際日期、相同時間與不知道日期的補登如何穩定排序，於 Stage 05 設計明確規則，不可假裝掌握不存在的歷史先後資訊。
- 若玩家看到未持有款式卻沒有在遊戲內收藏，Pikambler 仍把它視為模型中的已觀察款式，**不處理**和實際圖鑑不一致的情況。

### 2.3 遊戲新增款式時

- 系列款式清單與 `N` 應可配合遊戲更新調整；目前不承諾有官方資料串接、即時更新或自動偵測新款。
- **禁止**在調整 `N` 時，無提示地將過去在舊模型下的機率、已完成結果重算成新模型的歷史事實。
- Stage 05 必須決定如何保存或標記**模型版本與生效時間／歷史計算前提**。例如原先 `8/8` 已完成、遊戲新增第九款，現在可成為 `8/9`，但舊版 `8/8` 的判定與公式前提不能被靜默抹去。
- 多系列同類別的組合模型（如超市香蕉／蘑菇）屬後續候選功能，不是以 `N` 自動加總即可認定真實掉率等機率。

## 3. 理論機率契約（00.03～00.04）

**僅對符合本挑戰系列且被登記的觀察，使用下列教學假設：**

1. 本系列的 `N` 款在每次模型觀察中**各為 `1/N`**。
2. 每次模型觀察**相互獨立**，既有紀錄及玩家已觀察哪些款式不會改變任何指定款式的出現機率。
3. **沒有保底、個人權重、地點權重、取得來源權重或連敗補償**；上述都是理想化數學前提，**不是**真實遊戲規則的結論。
4. 來源不參與公式；不比較純點、混合點、散步或生活日誌的實際取得效率。
5. 對已觀察進度 `k/N`（`0 ≤ k ≤ N`），只在有效定義域內計算：

| 問題 | 理論公式與限制 |
|---|---|
| 下一次出現未觀察款式 | `(N-k)/N` |
| 下一次出現重複款式 | `k/N` |
| 從固定 `k/N` 階段開始，連續 `m` 次沒有新款 | `(k/N)^m`，`m ≥ 0`；期間因全為重複，`k` 保持不變 |
| 在接下來 `m` 次中至少一次有新款 | `1-(k/N)^m`；指的是**相對於起始已觀察集合**至少出現一個新款 |
| 第 `m` 次首次出現新款 | `(k/N)^(m-1) * (N-k)/N`，`m ≥ 1` 且 `k < N` |
| 待下一款的理論期望觀察數 | `N/(N-k)`，僅限 `k < N` |
| 從 `k/N` 直到模型完成的期望觀察數 | `Σ_(r=1)^(N-k) N/r`；`k = N` 時應明確顯示已完成，不以分母零計算 |

**不得誤解：**

- 理論尾端機率（如連續 30 次重複的機率）**不是**真實玩家百分位、實測排名或遊戲作弊證據。
- 有漏登或挑選性登記事件時，這些數字只能用來描述「依已登記資料構成的理論情境」，**不是完整真實歷程的精確罕見程度**。
- `5/8→6/8→7/8` 跨階段的完成時間，不可套用固定 `7/8` 重複機率，亦不可直接將「新款」當作每次成功率都相同的二項分布。
- 最後一款的幾何等待與完整系列集齊的時間分布是不同數學問題；完整完成時間分布與排容／動態規劃先列 Stage 17，不是 v1.0 必交功能。
- 公式中的「抽數」指**理論上連續觀察到此系列的次數**，不換算成實際天數或探測器使用次數。

## 4. 高中數學講義規則（00.01、00.08）

### 4.1 v1.0 四章

| 章 | 主題 | 對應問題 |
|---|---|---|
| 第 1 章：抽獎的基本規則 | 樣本空間、事件、古典機率 | 下一次出現新款的機率 |
| 第 2 章：連續槓龜的數學 | 獨立事件、乘法原理、餘事件、條件機率 | 連續重複、至少一次成功、賭徒謬誤 |
| 第 3 章：等待第一個成功 | 隨機變數、幾何分布、期望值 | 第幾次才新款、平均還要幾次、理論等待分布 |
| 第 4 章：從 `k/N` 到 `N/N` | 分階段機率、期望值加法、綜合應用 | 每進一款機率變化、整趟剩餘期望次數 |

- **不設第 0 章**的小學運算暖身；必要記號（如 `E(X)`）隨題解釋即可。
- 排列組合、排容原理、二項分布、完整集郵者問題等「綜合挑戰」等完成第 1～4 章再評估，不阻擋 v1.0。
- 六種規劃題型：A 下一次新／重複、B 連續重複、C 至少一次新款、D 第 `m` 次首見新款、E 等待下一款期望、F 分段至全部完成期望。**規劃六種；Stage 10 最低驗收為至少四種題型可由紀錄生成正確題目及解析，且第 1～4 章都要有對應可運作的教學題目**。
- 講義格式：**情境 → 已知 → 求 → 提示 → 列式 → 計算 → 解釋**；題目、提示、解答與娛樂性評語分離，後者不可改變數學事實。
- 參考：臺灣 108 課綱、均一教育平台的數學概念、**大考中心**歷屆學測／分科測驗的命題方式；**原創**題幹、數值與解析，不照抄或僅機械替換原題文字。
- 標明高一／高二／高三選修數甲及綜合延伸的界線；幾何分布不得籠統宣稱為所有學測考生必考內容。
- 所有題目明確註明理論模型，沒有實際遊戲掉率證據；不做真實掉率推論或 p-value 分析。

## 6. 非目標與未來候選（00.09）

### 6.1 明確不屬於此產品方向

- 推估、驗證或宣稱《Pikmin Bloom》真實掉率、公平性、隱藏權重與玩家間實測排名。
- 純點地圖、地理路線規劃（屬不同產品議題）。
- 付費、訂閱、廣告變現。
- 追蹤玩家實際有無收下花苗、種植、鍍金或完成遊戲內圖鑑；也不糾正兩者與模型已觀察進度的差距。

### 6.2 v1.0 不做；完成後可再評估

- 登入、個人雲端資料儲存、跨裝置自動同步、集中多用戶資料服務；即使未來加入多人使用，仍不等於要彙整樣本推估真實掉率。
- 社群排行榜、玩家分享圖卡／證書。
- 同一地標類別對應複數普通飾品系列（如超市不同裝飾系列）、一色多種變體、稀有飾品與鍍金系統。
- 排列組合綜合挑戰、完整集齊時間的理論分布、高階統計視覺化、答題模式與錯題本。
- 取得來源的統計圖表；基本來源欄位仍屬 v1.0 可選輸入。

### 6.3 v1.0 不採用的技術

- 自行經營後端 HTTP API；不整合遊戲官方／非官方資料 API。注意這不代表禁止使用瀏覽器的 IndexedDB、File API。
- 樹莓派常駐主機、LINE Bot、登入服務、付費雲端資料庫或伺服器端運算。
- React 或其他大型 UI 框架；以原生 HTML／CSS／TypeScript 練習基礎。

## 7. 隱私、備份與可靠性（00.10）

- 挑戰及觀察結果存於玩家自己使用的瀏覽器 **IndexedDB**；站台不主動將這些紀錄送至 Pikambler 自營伺服器、雲端資料庫或分析服務。
- 不要求姓名、Email、密碼與登入；沒有跨裝置自動同步。
- 玩家能查閱、更正、刪除紀錄，並手動 JSON 匯出、匯入。
- IndexedDB 是本機持久化儲存，**不是永久保證或備份**；站點資料遭清除、瀏覽器／裝置故障或無痕模式可能導致資料遺失。
- Cloudflare 提供網站檔案，不替玩家保存觀察歷史；**網路託管商仍可能處理必要的連線中繼資料，例如 IP 與請求日誌**，不可宣稱網站完全零資料處理。
- JSON 還原要驗證結構、版本、ID 關聯、款式與日期；正式覆蓋既有資料前須經使用者確認、保留救援途徑，失敗不可毀損原資料。
- 版本回滾只回復程式；**不**自動回滾瀏覽器 IndexedDB，資料格式演進要維持向後相容或有安全升級方案。
- 導入雲端／登入前必須重新審視隱私說明、帳號存取權限、資料同步衝突、成本與資料遷移；此工作**不屬 v1.0**。

## 8. 技術架構與學習原則

| 層 | v1.0 決策 | 邊界 |
|---|---|---|
| UI | 原生 HTML／CSS／TypeScript（手機優先） | 不直接呼叫資料庫底層；需可顯示錯誤 |
| 開發與建置 | Node.js + Vite `vanilla-ts` | Node.js 用於建置／開發，不是常駐後端 |
| 領域／計算 | 純 TypeScript 函式與題目模板 | 不依賴 UI、地點、來源或儲存機制 |
| 資料存取 | Repository（資料存取層） → IndexedDB | UI 經統一非同步介面操作；避免儲存技術散落各處 |
| 備份 | 有格式版本的 JSON | 提供匯出、驗證匯入、恢復 |
| 測試 | Vitest、人工情境測試、GitHub Actions | 檢查算式、歷史重播、匯入還原 |
| 部署 | Cloudflare Workers Static Assets、免費 `*.workers.dev` | 純靜態資源，不需要 Worker API 腳本；上線時重新核對官方設定與免費限制 |
| 版本控制 | Git + GitHub | 分支、提交、PR、自審、回滾 |

- **未來可擴充，不等於今天實作**：穩定的挑戰／觀察 ID、儲存格式版本、UI／數學／資料存取分離、非同步資料存取接口是目前必要的合理設計；不需預留大量未使用的雲端功能。
